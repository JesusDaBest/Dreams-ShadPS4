## Missing producer-count proof

The held-state capture did not record the two flattened-SRT values needed to distinguish a stale
host view from a genuinely empty producer:

- flattened word 41, read from SRT root + `0x64`, bounds the producer records;
- flattened word 18 contributes the output record bound.

The existing lightweight diagnostic `SHADPS4_DREAMS_PRODUCER_COUNT_READBACK=1` refreshes the
producer count before re-flattening the SRT. Interpret one focused run as follows:

- word 41 changes from zero to nonzero: investigate GPU-to-CPU / flattened-SRT coherency;
- word 41 remains zero: trace its real writer and publication edge;
- word 41 is nonzero but the final producer count remains zero: capture the producer predicate,
  ordered-count payload, returned prefix, computed total, and indirect X publication.

This is the highest-value next proof. Avoid broad tracing until it is resolved.

## `DS_ORDERED_COUNT` address-unit contradiction

The September 2 WIP changed generic and Dreams-specific counter indices to an x4 family. Examples:

- `0x142 -> 0x508` for `0x2bfebd3c`;
- `0x100 -> 0x400` for f030/5ac;
- per-pass counter strides `1 -> 4` for several compactors.

The intent was to treat M0's high half as a native dword-indexed ordered-count base. However,
commit `44a884e` and the still-present Python semantic tests require `0x500 -> 0x140` plus the
encoded offset (`0x142` for the primary producer operation), while WIP commit `f553e23` changes
the C++ to the x4 family (`0x508`). The WIP therefore contains a direct model-versus-C++
contradiction.

AMD Sea Islands documents the normal GDS M0 base and size in bytes but is terse for
`DS_ORDERED_COUNT`. Later AMD documentation maps M0 high-half bits `[15:2]` to the dword ordered
base, which also implies dividing the encoded high half by four for the host GDS dword index. The
older `/4` interpretation is better supported, but it still needs one controlled Liverpool test.

Runtime evidence also prevents a shortcut conclusion:

- a held-preview shader module used `0x508` for `0x2bfebd3c`, while host exact-replay constants
  and the sampled counter table still used the older `/4` family; that mixed-unit run published
  indirect X = 0, but its all-zero `/4` table did not observe the counter actually used by 2bf;
- the user experienced severe edit-mode lag in the full x4-family build, but no capture proves the
  address change caused the lag;
- its log showed no oversized dispatch before the stall;
- startup had new targeted cache misses and stale pipelines, so compilation/cache state remains a
  performance confounder.

Therefore neither address interpretation is recorded as verified here. Re-read the official AMD
Sea Islands definition, make generic lowering and every exact replay path use one coherent unit,
then test the two interpretations in isolation. Do not infer correctness from a fuller cube or a
nonzero counter alone.
